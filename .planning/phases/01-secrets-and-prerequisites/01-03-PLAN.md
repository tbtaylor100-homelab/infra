<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator terminal → OpenBao API | Operator token sent over HTTP to 192.168.1.210:8200. Token has write access to sys/policy and secret/*. |
| Shell environment → OpenBao | SECRET_KEY generated in shell; passed via env var to bao kv put. Value in shell history after echo. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure | SECRET_KEY in shell history | mitigate | Runbook uses variable capture pattern — `SECRET_KEY=$(openssl rand -hex 32)`. The kv put command uses `"$SECRET_KEY"` variable reference, not the literal value. Operator should clear shell history if this is a shared machine. |
| T-03-02 | Elevation of Privilege | Root token used for policy write | accept | Root token is required for sys/policy/write. This is a one-time provisioning operation on a homelab; token is not stored anywhere persistent after the session. |
| T-03-03 | Tampering | Policy overwrite drops homelab/ci | mitigate | Pre-flight Task 1 verifies eso-policy.hcl contains both paths before operator runs bao policy write. Task 2 acceptance criteria explicitly checks homelab/ci is still present after apply. |
| T-03-04 | Repudiation | No audit trail of secret creation | accept | OpenBao audit log (if enabled) captures the write. This is a homelab with a single operator; non-repudiation is not a requirement. |
</threat_model>
