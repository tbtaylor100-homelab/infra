# Domain Pitfalls: AIOStreams on k3s

**Domain:** Self-hosted AIOStreams deployment (Stremio filtering proxy)  
**Researched:** 2026-05-11  
**Confidence:** MEDIUM (HIGH for ESO patterns, MEDIUM for AIOStreams specifics)

---

## Critical Pitfalls

### Pitfall 1: SECRET_KEY Rotation After Deployment Invalidates All User Configs

**What goes wrong:**
AIOStreams encrypts user configuration using the `SECRET_KEY` as a seed for PBKDF2-derived encryption keys (AES-256-GCM). If you change `SECRET_KEY` after users have added the addon and saved credentials, their saved configurations become permanently unreadable garbage. Stremio will continue to reference the broken addon manifest URL, but any attempt to load or reconfigure will fail with decryption errors.

**Why it happens:**
- AIOStreams uses `SECRET_KEY` to derive encryption keys via PBKDF2 + user password
- Encrypted config is stored server-side, bound to that key
- Changing the key breaks the derivation; old configs cannot be decrypted
- Stremio caches the old manifest URL; the config is "burned in" until uninstalled + reinstalled

**Consequences:**
- Silent config loss — no error on the addon side, just "can't read this config"
- Users must uninstall and reinstall the addon in Stremio (not just reload)
- Any pre-saved API keys, Torrentio credentials, filter rules are lost
- For a homelab single-user instance, this is catastrophic on redeploy

**Prevention:**
- Generate a strong, stable `SECRET_KEY` *before first deployment* using `openssl rand -hex 32`
- Store it in OpenBao `secret/data/aiostreams/production` and treat as immutable
- If you must rotate the key (security incident), plan user communication and config migration
- Document the SECRET_KEY generation step in the runbook as non-repeatable
- Consider using a Kubernetes Secret for deterministic generation (e.g., from a fixed seed in the GitOps repo, not random)

**Detection:**
- User reports: "addon loads but won't let me configure anything"
- Logs: Watch for decryption errors or "invalid user config" messages
- Check pod logs: `kubectl logs -n aiostreams deployment/aiostreams | grep -i decrypt`
- Monitor ESO sync success but pod startup complaints about config

**Sources:**
- [AIOStreams Configuration Wiki](https://github.com/Viren070/AIOStreams/wiki/Configuration)
- [AIOStreams Deployment Guide](https://github.com/Viren070/AIOStreams/wiki/Deployment)

### Pitfall 2: BASE_URL Mismatch Between LAN IP and Localhost Breaks Manifest Installation

**What goes wrong:**
If `BASE_URL` is set to `localhost:3000` but AIOStreams is accessed from a LAN IP (e.g., `192.168.1.100:3000`), the manifest URL generated by AIOStreams will include `localhost`. Stremio clients running on other devices on the LAN cannot reach `localhost` — they interpret it as their own machine. The addon fails to load in Stremio with a "cannot reach addon" error.

Conversely, if `BASE_URL` is a LAN IP and accessed from localhost, Stremio will generate installation URLs pointing to the LAN IP, breaking local development/testing.

**Why it happens:**
- Stremio uses `BASE_URL` to generate the manifest URL: `stremio://install?url=${BASE_URL}/manifest.json`
- Every Stremio client resolves `localhost` relative to *its own* machine, not the AIOStreams server
- `BASE_URL` is baked into the addon's manifest and saved in Stremio's config when installed
- AIOStreams does provide `STREAM_URL_MAPPINGS` and `REQUEST_URL_MAPPINGS` for advanced cases, but not for the base URL itself

**Consequences:**
- Addon appears to install but fails with 404/connection refused in Stremio
- Difficult to diagnose because the error appears in Stremio's logs, not AIOStreams' logs
- Affects *all* non-localhost devices
- URL remapping options exist but are fragile and not intuitive

**Prevention:**
- If exposing via LAN IP (MetalLB LoadBalancer), set `BASE_URL` to the LAN IP + port
- If using a hostname (future work per PROJECT.md), use the FQDN
- **Do NOT use `localhost` in production** — it will break any client not on the same machine
- Document in runbook: "BASE_URL must match how clients will access the service"
- For homelab, use the MetalLB LoadBalancer IP address (e.g., `http://192.168.1.100:3000`)
- Test from a non-localhost device before considering deploy complete

**Detection:**
- Stremio shows "Cannot reach addon" when trying to load it
- Addon installs but is immediately marked as unavailable
- Check AIOStreams logs: should show successful requests to `/manifest.json` but Stremio can't reach them
- Verify: `curl http://<BASE_URL>/manifest.json` from a different machine on the LAN

**Sources:**
- [Stremio Addon Manifest Guide](https://stremio.github.io/stremio-addon-guide/step1)
- [AIOStreams Setup Guide](https://guides.viren070.me/stremio/addons/aiostreams/setup)

### Pitfall 3: ESO-Policy Scope Not Extended — ExternalSecret Fails Silently

**What goes wrong:**
The project context states: "OpenBao eso-policy must be extended to cover `secret/data/aiostreams/*` before ESO sync will work." If you deploy the ExternalSecret CR without extending the policy, the ExternalSecret will show a `Status.Condition` of `false` with error "unable to validate store" — but the secret *will not sync*. The AIOStreams pod will start and crash immediately because the `SECRET_KEY` and Real-Debrid credentials are not in the Kubernetes Secret.

The pod logs will show vague startup errors about missing environment variables, not pointing to the actual root cause (OpenBao policy denial).

**Why it happens:**
- External Secrets Operator attempts to authenticate to OpenBao using a Kubernetes auth role bound to a policy
- The existing `eso-policy` in OpenBao is scoped only to `secret/data/homelab/ci`
- Any request for `secret/data/aiostreams/*` is denied at the Vault policy level
- ESO cannot read the secret path; it returns a 403 Forbidden
- The ExternalSecret CR still exists and reports "Sync Failed" but this is easy to miss in initial deployments

**Consequences:**
- AIOStreams pod crashes with "SECRET_KEY missing" even though it's in OpenBao
- Debugging is confusing: the secret exists in OpenBao but the pod can't see it
- ArgoCD may mark the Application as "OutOfSync" but not "Degraded" if pods are just restarting
- Easy to waste time troubleshooting AIOStreams config instead of the permissions issue

**Prevention:**
- **Before deploying:** Extend the `eso-policy` in OpenBao to include:
  ```hcl
  path "secret/data/aiostreams/*" {
    capabilities = ["read", "list"]
  }
  ```
- Verify the policy is applied: `bao policy read eso-policy`
- Deploy ExternalSecret and immediately check status: `kubectl get externalsecrets -n aiostreams -o wide`
- Look for `SYNC_STATUS = true` (not false)
- Test the policy manually before deploying: use `bao kv get secret/aiostreams/production` with the Kubernetes auth role

**Detection:**
- `kubectl describe externalsecret aiostreams-secrets -n aiostreams` shows condition `SyncFailed`
- `kubectl logs -n aiostreams deployment/aiostreams` shows "SECRET_KEY: required environment variable not set"
- `kubectl logs -n external-secrets-system deployment/external-secrets` shows "permission denied" or "invalid AppRole token"
- OpenBao audit log shows 403 Forbidden for `secret/data/aiostreams` requests

**Sources:**
- [External Secrets Operator + Vault Configuration](https://external-secrets.io/latest/provider/hashicorp-vault/)
- [PROJECT.md constraint: eso-policy scope](file:///C:/repos/infra/.planning/PROJECT.md)

## Configuration Gotchas

### Gotcha 1: WHITELISTED_REGEX_PATTERNS Format — JSON Array, Not Comma-Separated

**What goes wrong:**
The environment variable `WHITELISTED_REGEX_PATTERNS` must be a JSON array of regex strings, but it's easy to assume it's comma-separated or newline-separated plain text. If you pass a malformed format, AIOStreams will either silently ignore the patterns (causing the filter to not activate) or crash at startup with a JSON parsing error.

Example malformed formats:
- `WHITELISTED_REGEX_PATTERNS="pattern1,pattern2"` ❌ (comma-separated)
- `WHITELISTED_REGEX_PATTERNS="pattern1\npattern2"` ❌ (newline-separated)
- `WHITELISTED_REGEX_PATTERNS='pattern1'` ❌ (single quoted string, not array)

Correct format:
- `WHITELISTED_REGEX_PATTERNS='["pattern1","pattern2"]'` ✅

**Why it happens:**
- JSON arrays in environment variables are non-intuitive; many people expect plain text delimiters
- AIOStreams documentation doesn't explicitly show an example of the full format
- Escaping quotes in shell/Kubernetes manifests is error-prone

**Consequences:**
- Filter rules silently don't apply; users see unfiltered RD-blocked results
- If you're catching the parsing error, startup fails with cryptic JSON error
- The problem is silent enough that you might not notice until testing with actual Stremio

**Prevention:**
- Use JSON validators before deploying: paste the patterns into a JSON validator
- In Kubernetes Secret or ESO, store as a properly escaped JSON array
- Example YAML:
  ```yaml
  WHITELISTED_REGEX_PATTERNS: '["/^(?!.*(?:RD-BLOCKED|INFRINGING)).*$/i"]'
  ```
- Test the pattern in AIOStreams UI before committing to a K8s manifest
- Document in runbook: "Regex patterns must be JSON array format"

**Detection:**
- Deploy and check: do the regex filters appear in the AIOStreams UI?
- Stremio shows unfiltered (RD-blocked) results despite filter config
- Check pod logs: `kubectl logs -n aiostreams deployment/aiostreams | grep -i regex`
- If no errors, patterns are likely malformed but silently ignored

**Sources:**
- [AIOStreams .env.sample on GitHub](https://github.com/Viren070/AIOStreams/blob/main/.env.sample)
- [WHITELISTED_REGEX_PATTERNS documentation](https://guides.viren070.me/stremio/addons/aiostreams/documentation)

### Gotcha 2: FORCED_SERVICE_CREDENTIALS Format — `serviceId.credentialId=value`

**What goes wrong:**
The format for `FORCED_SERVICE_CREDENTIALS` must match `serviceId.credentialId=value`, but for Real-Debrid, the `credentialId` is `apiKey`, not `token` or `api_key` (with underscore). If you use the wrong credential ID, the Real-Debrid credential is silently ignored or causes a cryptic validation error, and AIOStreams has no Real-Debrid integration.

Example malformed formats:
- `FORCED_SERVICE_CREDENTIALS=realdebrid.token=...` ❌ (wrong credential ID)
- `FORCED_SERVICE_CREDENTIALS="realdebrid=..."` ❌ (missing credentialId)
- `FORCED_SERVICE_CREDENTIALS=realdebrid_apiKey=...` ❌ (wrong separator)

Correct format:
- `FORCED_SERVICE_CREDENTIALS=realdebrid.apiKey=YOUR_API_KEY` ✅

**Why it happens:**
- Each debrid service (RealDebrid, AllDebrid, Premiumize, TorBox) has different credential IDs
- The documentation doesn't clearly list all credential IDs, so you have to guess or read the source code
- Copy-paste from similar projects with different naming conventions

**Consequences:**
- Real-Debrid integration is silently not activated
- Users see no streams because Torrentio is not configured with RD credentials
- Configuration errors are hard to spot; the addon starts successfully but provides no value
- Very difficult to debug without reading the AIOStreams source or checking pod logs carefully

**Prevention:**
- Before writing the Secret in OpenBao, verify the credential ID in [AIOStreams .env.sample](https://github.com/Viren070/AIOStreams/blob/main/.env.sample)
- Document in runbook: "For Real-Debrid, use credentialId=apiKey"
- Test the config by checking Stremio: do streams appear from Torrentio?
- If unsure, export a config from the AIOStreams UI after manually setting RD credentials, and note the format

**Detection:**
- AIOStreams starts but Torrentio shows "0 streams" in Stremio
- Check the AIOStreams configuration UI: is Real-Debrid listed as active?
- Pod logs: `kubectl logs -n aiostreams deployment/aiostreams | grep -i realdebrid`
- Inspect the Secret: `kubectl get secret aiostreams-secrets -n aiostreams -o jsonpath='{.data}'` (base64 decoded)

**Sources:**
- [AIOStreams .env.sample](https://github.com/Viren070/AIOStreams/blob/main/.env.sample)
- [FORCED_SERVICE_CREDENTIALS GitHub Issue #266](https://github.com/Viren070/AIOStreams/issues/266)

### Gotcha 3: SQLite Concurrency — Multiple Stremio Clients or Background Tasks Cause Locking

**What goes wrong:**
AIOStreams uses SQLite for caching and user config storage. SQLite supports concurrent reads but *only one writer at a time*. If multiple Stremio clients hit AIOStreams simultaneously (e.g., querying for streams, saving filters), or if a background task (metadata scraping, cache refresh) runs while a client is configuring, SQLite will lock and delay responses. In homelab scenarios with low throughput, this is usually acceptable, but it can manifest as:
- Slow response times on the UI configuration page
- Stremio timeouts if AIOStreams is busy
- Database locked errors in logs under high concurrency

**Why it happens:**
- SQLite uses file-level locks; only one process can write at any time
- AIOStreams doesn't use connection pooling or queuing for writes
- Multiple Stremio clients on the LAN can generate concurrent requests
- PVC in Kubernetes (ReadWriteOnce) ensures only one pod can access the file, but doesn't prevent concurrent threads/processes inside the pod

**Consequences:**
- For a single-user homelab, this is usually not a problem
- If you scale to multiple pods later without replacing SQLite, concurrency issues will become severe
- Slow metadata updates or config saves during periods of high Stremio usage
- Not a showstopper, but a silent quality-of-life issue

**Prevention:**
- Accept that SQLite is adequate for single-pod, single-user homelab deployments
- Document in ARCHITECTURE.md that SQLite is suitable for current scale
- **Single pod requirement:** Ensure `replicas: 1` in the Deployment (already in PROJECT.md out-of-scope)
- If you later add multiple pods or need better concurrency, migrate to PostgreSQL
- Consider using SQLite WAL (write-ahead logging) mode if AIOStreams supports it, to improve concurrency

**Detection:**
- Stremio shows slow loading times when configuring the addon
- Pod logs show "database is locked" or timeout errors
- Check Kubernetes: verify only 1 pod is running
- Monitor pod CPU/memory: if both are low but responsiveness is slow, SQLite locking is likely

**Sources:**
- [SQLite Concurrency Documentation](https://vadosware.io/post/sqlite-is-threadsafe-and-concurrent-access-safe-but/)
- [SQLite in Kubernetes with PVC](https://www.jeeviacademy.com/deploying-a-simple-sqlite-app-on-kubernetes-with-persistent-storage-pvc/)

## ESO/Secrets Pitfalls

### Pitfall 4: ExternalSecret Sync Ordering — Namespace Must Exist Before ExternalSecret

**What goes wrong:**
ArgoCD applies resources in waves. If you don't use sync waves to order the creation of the `aiostreams` namespace *before* the `ExternalSecret` CR, ArgoCD may attempt to create the ExternalSecret in a namespace that doesn't exist yet. The ExternalSecret will fail with "namespace not found" and the sync will fail. Even after the namespace is eventually created, the ExternalSecret may not immediately reconcile.

**Why it happens:**
- ArgoCD's default sync order is: create all resources, then wait for health
- CRDs and namespaces don't have special ordering by default
- External Secrets Operator tries to validate and sync immediately upon resource creation
- If the namespace doesn't exist, validation fails before the Secret can sync

**Consequences:**
- Initial ArgoCD sync fails; manual intervention required
- `kubectl get application aiostreams` shows `OutOfSync` and `Degraded`
- Users must manually re-sync or delete the ExternalSecret to retry after namespace creation
- Reduces confidence in GitOps automation

**Prevention:**
- Use ArgoCD sync waves to order resource creation:
  ```yaml
  apiVersion: v1
  kind: Namespace
  metadata:
    name: aiostreams
    annotations:
      argocd.argoproj.io/sync-wave: "-2"  # Create first
  ```
  ```yaml
  apiVersion: external-secrets.io/v1beta1
  kind: ExternalSecret
  metadata:
    name: aiostreams-secrets
    namespace: aiostreams
    annotations:
      argocd.argoproj.io/sync-wave: "-1"  # Create after namespace
  ```
- Apply `CreateNamespace=true` as a sync option in the ArgoCD Application
- Document the sync wave pattern in the ArgoCD Application manifest

**Detection:**
- `kubectl get application aiostreams -o wide` shows `Degraded: OutOfSync`
- `argocd app sync aiostreams` shows "namespace not found" errors
- ExternalSecret status: `kubectl get externalsecrets -n aiostreams -o wide` shows `SYNC_STATUS: false` with namespace errors

**Sources:**
- [ArgoCD Sync Waves and Ordering](https://argo-cd.readthedocs.io/en/latest/user-guide/sync-options/)
- [How to Handle CRD and CR Ordering with ArgoCD](https://oneuptime.com/blog/post/2026-02-26-how-to-handle-crd-and-cr-ordering-with-argocd/)

### Pitfall 5: Vault Path Format Mismatch — `secret/data/` vs `secret/`

**What goes wrong:**
External Secrets Operator expects the Vault path in a specific format. For the KV v2 secrets engine (which OpenBao is using), the path must include `data/` in the request path: `secret/data/aiostreams/production`. If you misconfigure the ESO SecretStore to use `secret/aiostreams/production` (without the `data/` segment), the request will 404 in Vault and the secret will not sync.

The confusion arises because:
- In Vault CLI, you use `vault kv get secret/aiostreams/production` (no `data/`)
- But the HTTP API path is `/v1/secret/data/aiostreams/production` (with `data/`)
- ESO speaks HTTP directly, so it needs the full path

**Why it happens:**
- Vault KV v2 stores secrets at the mount point `secret` but the HTTP API path includes `data/` as a reserved word
- Documentation is inconsistent: some examples show the CLI path, others show the HTTP path
- Easy mistake when migrating from KV v1, which didn't require `data/`

**Consequences:**
- ExternalSecret shows "unable to read secret: path not found" errors
- AIOStreams pod starts but environment variables are missing (no SECRET_KEY, no credentials)
- Silent failure if you don't check ExternalSecret status carefully

**Prevention:**
- In the `ClusterSecretStore`, explicitly use the HTTP API path:
  ```yaml
  path: secret/data/aiostreams/production
  ```
- Verify by testing the path manually:
  ```bash
  kubectl exec -it <eso-pod> -- curl -H "Authorization: Bearer $VAULT_TOKEN" \
    https://192.168.1.210:8200/v1/secret/data/aiostreams/production
  ```
- Document in the runbook: "Vault paths in ESO must include `/data/` for KV v2"

**Detection:**
- `kubectl describe externalsecret aiostreams-secrets -n aiostreams` shows error "path not found"
- `bao kv get secret/aiostreams/production` works fine from CLI, but ESO still fails
- Check ESO controller logs: `kubectl logs -n external-secrets-system deployment/external-secrets | grep aiostreams`

**Sources:**
- [External Secrets Operator Vault Provider Documentation](https://external-secrets.io/latest/provider/hashicorp-vault/)
- [Vault KV v2 API Documentation](https://developer.hashicorp.com/vault/api-docs/secret/kv-v2)

## Operational Risks

### Risk 1: Torrentio Blocking k3s Pod IP — Streams Return 403

**What goes wrong:**
Torrentio and other strem.fun addons (which AIOStreams uses for stream aggregation) block certain IP ranges to prevent abuse. If your k3s cluster is running on an IP range that Torrentio considers blocked (e.g., Oracle Cloud VPS ranges), when AIOStreams attempts to fetch streams from Torrentio, the request will be rejected with a 403 Forbidden. Users will see no streams in Stremio.

This is particularly concerning for homelab deployments using cloud VMs for k3s (though the PROJECT.md context suggests this is a local Proxmox VM, so risk is LOW).

**Why it happens:**
- Torrentio rate-limits and blocks abusive clients
- Cloud provider IP ranges (especially datacenter IPs) are often blocked
- AIOStreams makes requests on behalf of the Stremio client, so the source IP is the k3s pod's IP
- Even if your LAN IP is whitelisted, the k3s pod's internal IP might not be

**Consequences:**
- AIOStreams appears to work but provides zero streams
- Difficult to diagnose; users think AIOStreams is broken when the real issue is IP blocking
- If using a VPN workaround, performance degrades and the VPN may also get blocked over time

**Prevention:**
- Confirm k3s cluster is on a residential/homelab IP range (not cloud datacenter)
- For the PROJECT.md setup (local Proxmox VM on home network), this is not a concern
- If deploying to cloud later, consider:
  - Using a residential proxy (expensive, not recommended for homelab)
  - Switching to different stream sources that don't block (may have lower availability)
  - Documenting as a limitation of cloud-based deployments

**Detection:**
- AIOStreams pod starts successfully
- Stremio shows "0 streams" when querying
- Check AIOStreams logs: `kubectl logs -n aiostreams deployment/aiostreams | grep -i torrentio`
- Manually test from pod: `kubectl exec -it <aiostreams-pod> -- curl https://torrentio.strem.fun/manifest.json`

**Sources:**
- [AIOStreams Deployment Guide — VPN Workaround](https://github.com/Viren070/AIOStreams/wiki/Deployment)
- [Torrentio IP Blocking Issue](https://github.com/Viren070/AIOStreams/issues/509)

### Risk 2: Real-Debrid API Key Exposed in ArgoCD Logs or Application Manifest

**What goes wrong:**
If the Real-Debrid API key is accidentally committed to the git repo or logged in plain text during deployment, it's exposed to anyone with access to the repo or logs. This is a security issue because the API key can be used to:
- Query the user's RD account
- Modify RD settings
- Exhaust rate limits
- Access the user's debrid content

This is mitigated by using OpenBao + ExternalSecret, but it's a risk if you deviate from the pattern (e.g., hardcoding the key in a Kubernetes Secret manifest).

**Why it happens:**
- GitOps workflows tempt you to store everything in git for reproducibility
- Kubernetes Secrets in manifests are just base64-encoded (not encrypted) by default
- ArgoCD logs can be verbose; they might echo environment variables
- Easy mistake when testing: applying a Secret directly instead of via ESO

**Consequences:**
- Real-Debrid account compromise
- Rate-limit exhaustion (someone abuses your API key)
- Loss of debrid service until key is rotated
- Regulatory/privacy issue if RD account is tied to personal data

**Prevention:**
- **Never commit plaintext secrets to git.** Use the ESO + OpenBao pattern exclusively.
- Verify: grep the repo for "apiKey" or "FORCED_SERVICE_CREDENTIALS" — should find none
- Review git history: `git log -p --all -S "apiKey"` to catch accidental commits
- Use pre-commit hooks to prevent secrets in git (e.g., `pre-commit` with `detect-secrets`)
- Rotate the API key immediately if suspected exposure
- Document in runbook: "Secrets are managed in OpenBao, not git"

**Detection:**
- Code review: any manifest with plain-text credentials gets rejected
- Git audit: check git log for accidental commits
- ArgoCD: check application logs for verbose credential output

**Sources:**
- ADR-011 in PROJECT.md context (Kubernetes auth role pattern)
- [OWASP: Secrets Management in Cloud-Native Applications](https://owasp.org/www-community/attacks/Credential_Stuffing)

### Risk 3: PVC Data Loss — SQLite Database Disappears on Node Eviction

**What goes wrong:**
AIOStreams stores user configs and caches in a PVC with `storageClassName` and `accessMode: ReadWriteOnce`. If the Proxmox node hosting the PVC fails or the pod is evicted, the PVC may not be reattached to another node (since ReadWriteOnce means only one node can mount it at a time). If the node's storage is lost, the PVC is permanently deleted by your storage provider, and all user configs and caches are lost.

This is a lower risk for a homelab with one node, but it's worth planning for.

**Why it happens:**
- ReadWriteOnce (RWO) PVCs can only be mounted on one node at a time
- If the pod is evicted, the PVC persists but is orphaned
- If the node's storage fails, the PVC data is lost unless backed up
- k3s doesn't automatically back up PVCs

**Consequences:**
- Users must reconfigure AIOStreams (re-add Real-Debrid credentials, re-apply filters)
- Loss of cached metadata (minor impact; re-cached automatically)
- Single point of failure if running on a single node

**Prevention:**
- Implement a backup strategy for the PVC:
  - Use Proxmox snapshots (if running on Proxmox, backup the VM's storage)
  - Implement in-cluster backups (e.g., Velero, Kasten)
  - Regular manual exports of user config
- For a single-node homelab, document the recovery procedure: "If PVC is lost, restore from backup or reconfigure"
- Consider marking the PVC with a label `backup=required` for future automation
- Store a copy of the initial configuration (WHITELISTED_REGEX_PATTERNS, FORCED_SERVICE_CREDENTIALS) in the Deployment manifest for quick recovery

**Detection:**
- Pod starts but shows "no persistent data" or "database not found"
- PVC is in `Pending` or `Lost` state: `kubectl get pvc -n aiostreams`
- Check Kubernetes events: `kubectl describe pvc -n aiostreams`

**Sources:**
- [Kubernetes PVC Documentation](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)
- [k3s Local Storage Documentation](https://docs.k3s.io/storage)

## Phase-Specific Warnings

| Phase Topic | Likely Pitfall | Mitigation |
|-------------|---------------|----------|
| **Secrets Generation** | SECRET_KEY generated randomly each deployment | Generate once, store in OpenBao, treat as immutable; document in runbook |
| **OpenBao Policy Prep** | eso-policy not extended to `secret/data/aiostreams/*` | Extend policy before deploying any K8s resources; verify with `bao policy read eso-policy` |
| **ArgoCD Application** | Sync waves not configured; namespace created after ExternalSecret | Use sync waves: namespace at -2, ExternalSecret at -1 |

| **Regex Patterns** | WHITELISTED_REGEX_PATTERNS not in JSON array format | Validate JSON before deploying; test patterns appear in AIOStreams UI |
| **Post-Deploy Validation** | Skipped; assumption that if pod is running, everything works | Checklist: addon loads in Stremio, streams appear, filters work, config persists |
| **SECRET_KEY Rotation (if needed)** | Attempted without user communication | Treat as a breaking change; users must reinstall addon; document in ADR |

## Summary

**Most critical to prevent:**
1. **SECRET_KEY rotation** — impossible to recover from without user reinstall
2. **ESO policy mismatch** — silent failure that looks like config issues
3. **BASE_URL mismatch** — breaks addon installation for LAN clients
4. **Secrets in git** — security incident

**Easiest to miss:**
- WHITELISTED_REGEX_PATTERNS JSON format
- FORCED_SERVICE_CREDENTIALS credentialId mismatch (apiKey vs token)
- ExternalSecret namespace ordering in ArgoCD

**For the homelab (low-risk):**
- SQLite concurrency (single user, acceptable)
- Torrentio IP blocking (residential IP, not a concern)
- PVC data loss (single node, backup is sufficient)
